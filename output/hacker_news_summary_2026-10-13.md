Ledger 确认在一部用于窃取加密货币的被篡改 Ledger Nano X 设备中发现了一个复杂的硬件植入物，即“间谍芯片”。此事件凸显了一类针对性的供应链式攻击，受害者会通过邮件收到欺诈性的“替换”设备。

## 5. Redesigning source control at Anthropic

**原文标题**: Redesigning source control at Anthropic

**原文链接**: [https://www.anthropic.com/engineering/redesigning-source-control](https://www.anthropic.com/engineering/redesigning-source-control)

Anthropic recently developed **Scion**, an in-house source control system, to replace Git after AI-driven development caused code merge rates to skyrocket from 2,500 to over 30,000 per day. As Claude began autonomously iterating on research and building services, Git’s decentralized, human-scale architecture became a massive bottleneck for Anthropic’s 100GB+ monorepo.

**Core Principles of Scion:**
Scion was designed specifically for "agent-scale" software development, moving away from Git’s offline-first model toward a centralized, API-driven architecture:
*   **Always-Online Clients:** Since most users are AI agents or CI jobs, Scion assumes constant connectivity, allowing the server to handle complex computations like history and blame.
*   **Changeset Model:** Instead of heavy "packfiles," Scion uses a write-ahead log of changesets. This enables lock-free, incremental commits where the cost scales with the size of the change, not the repository.
*   **Tiered Caching:** Using a system of local daemons and regional caches, Scion delivers 99% hit rates. This reduced Anthropic’s infrastructure footprint by 200x and improved CI checkout speeds by two orders of magnitude (from minutes to seconds).
*   **Sparse/Virtualized Checkouts:** Clients only fetch the specific data they need, significantly reducing data traffic.

**The Role of AI:**
The project serves as a case study for the "agentic" era of programming. Claude was both the cause of the scaling crisis and the primary tool used to solve it. A small team of just seven people built Scion and a new code review tool (**Antique**) in five months. In one instance, Claude Mythos Preview optimized a handwritten ingestion pipeline to be 4x faster while using 20x less memory. Anthropic suggests that as AI tools become more prevalent, other organizations will eventually need to move beyond traditional developer infrastructure to support this new scale of productivity.

## 9. 11 year old unsoundness bugs found in Rust borrow checker

**原文标题**: 11 year old unsoundness bugs found in Rust borrow checker

**原文链接**: [https://github.com/rust-lang/rust/issues/164250](https://github.com/rust-lang/rust/issues/164250)

A significant soundness hole in the Rust borrow checker, identified as issue #164250, was recently disclosed. The bug allows users to bypass a struct's lifetime requirements—specifically `'static` bounds—through covariant field assignment. While a struct may be defined to only accept `'static` data, the borrow checker fails to enforce this requirement during direct field updates, allowing short-lived local references to be assigned to fields the compiler believes are long-lived.

The primary danger occurs when the `Drop` trait is executed. Because the compiler incorrectly assumes the stored data is `'static`, the `Drop` implementation can safely perform actions that are illegal for local references, such as spawning threads or moving the data into global storage. This results in classic memory unsafety, including stack-use-after-scope, use-after-free errors, and segmentation faults.

Despite being present in the compiler for approximately 11 years—with some variations reproducible as far back as Rust 1.4—the bug went unnoticed until now. The Rust Types Team has assigned the issue a **P-high** priority. Project contributors noted that while the unsoundness is a "worst-kind" bug, it is unlikely to have caused widespread accidental memory unsafety because exploiting it typically requires a specific or intentionally malicious `Drop` implementation.

The discovery underscores the importance of the Rust team's ongoing "Project Zero" and the development of the next-generation trait solver, both of which aim to minimize foundational type system risks. Due to the high volume of traffic and potential for noise, the GitHub issue was temporarily locked to collaborators.
